# 阶段 7：内存复核、基底 tint 修复与可读性对照

> 一句话结论：**「206 个瓦片吃掉 508 MB」是测量口径问题，不是泄漏；不改虚拟化。**
> 但复核过程中查出一个真缺陷：阶段 2 想保留的那一层 18% 基底 tint，
> 在悬浮窗和侧边栏上其实**一层都没画上**——修复后亮壁纸下悬浮窗对比度
> 3.11 → 3.92、侧边栏 3.42 → 4.21，主窗口不变。

原始证据：`phase7-memory.json`、`readability-before.json`、`readability-after.json`。
截图含真实桌面项目名，按 `.gitignore` 不入库，留在本地 `docs/ui-acrylic-final/`。

---

## 一、为什么重查内存

阶段 4 记的是 220 项目 / 206 瓦片 / **507.9 MB 工作集**，但托管堆只有 30 MB。
这两个数字对不上：如果真是 206 个瓦片吃掉的，托管堆不会这么小。
旧报告把它写成「`WrapPanel` 不虚拟化 → 内存随项目数线性涨，属于架构层问题」，
并建议下一步做 `VirtualizingWrapPanel` 原型。做之前先确认「500 MB 到底是什么」。

---

## 二、测量方法（只动测试工具，未改业务代码）

`tests/DeskLanes.UiSnapshot` 新增两个模式：

| 模式 | 作用 |
|---|---|
| `mem` | 同一进程逐层拆除：原始 → 强制 GC → 裁剪工作集 → 摘文字投影 → 摘图标 → 卸载瓦片视觉树，每步记四个口径 |
| `memtoggle` | 连续 12 次「分类导航 ↔ 自由分区」切换，画「切换次数 → 内存」曲线，判定是否泄漏 |

`perf200` 的指标也从单看 `WorkingSet64` 扩成四个：`working_set_mb` /
`peak_working_set_mb` / `trimmed_working_set_mb` / `private_mb`。

口径说明：

- `WorkingSet64` 由 **Windows 按整机内存压力**管理，单次读数只是当时驻留了多少页，
  不等于进程真实占用；`SetProcessWorkingSetSize(-1,-1)` 能把它立刻还回去。
- `PrivateMemorySize64`（私有提交）才是进程真正要到的内存。
- `GC.GetTotalMemory` / `GCMemoryInfo.HeapSizeBytes` 看托管对象。

## 三、结果

### 1. 稳态内存随项目数的曲线（`mem`，同一 Release 构建）

| 批量项 | 实体化瓦片 | WS 原始 | **WS 裁剪后** | **私有提交** | 托管堆 |
|---:|---:|---:|---:|---:|---:|
| 0 | 8 | 142.5 MB | 13.3 MB | 88.7 MB | 2.9 MB |
| 50 | 51 | 152.2 MB | 29.2 MB | 106.6 MB | 4.6 MB |
| 205 | 206 | 170.4 MB | 34.4 MB | 128.6 MB | 12.6 MB |
| 500 | 501 | 222.1 MB | 41.1 MB | 150.9 MB | 22.5 MB |

**每多一个瓦片约 +0.09 MB 私有提交 / +0.04 MB 托管堆**，是线性但很轻的常驻成本。
「500 MB」这个量级在稳态里根本不存在。

### 2. 连续切换不是泄漏（`memtoggle`，205 个批量项）

私有提交：`131.9 → 139.2（热身）→ 151.6 → 163.1 → 165.8 → 166.6 → 164.0 MB`，
第 5 次之后**走平并在 163~167 之间抖动**；`after_gc_trim` 回落到 **138.5 MB 私有 / 11.4 MB 托管 / 49.2 MB WS**。
切换时另一套视图（自由分区会实体化 220 个瓦片）会被实例化，加上 GC 没有立刻回收，
所以读数先涨一段；**不是随切换次数累积的泄漏**。

### 3. 复跑 `perf200`（3 次，同一二进制）

| 次 | WS | 峰值 WS | **裁剪后 WS** | **私有提交** | 托管堆 | 布局切换 |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 200.8 MB | 200.8 MB | **30.3 MB** | 276.0 MB | 29.6 MB | 324.1 ms |
| 2 | 201.2 MB | 201.2 MB | **30.8 MB** | 279.0 MB | 29.5 MB | 319.1 ms |
| 3 | 196.9 MB | 196.9 MB | **30.7 MB** | 277.4 MB | 29.7 MB | 308.3 ms |

托管堆 29.6 MB 与阶段 4 的 30.0 MB 几乎一致 —— **对象数量没变**。
变化的是系统当时愿意让这个进程驻留多少页：507.9 → 200 MB，裁剪后都回到 30 MB。
阶段 4 那组数字是在不同的整机内存状态下取的，`WorkingSet64` 把它记成了「占用」。

> 附带纠正：阶段 4 报告里「关掉投影省 1.7%」也是同一个口径问题——
> 摘掉 210 个 `Effect` 后没有强制 GC / 裁剪，WS 本来就不会立刻掉。
> 「投影无可测开销」这个结论仍然成立，但那 1.7% 不能当证据。

### 4. 决策：不做虚拟化

- 500 个项目时稳态私有提交约 151 MB，不是 500 MB 级；
- `WrapPanel` 换成虚拟化面板会动到拖拽、项目指派、自由分区几何与选中态，
  而阶段 6 已经冻结视觉与交互基线；
- 收益/风险不划算。**保留 `WrapPanel`，不引入新的第三方依赖，不改数据模型与命令。**
- 旧报告里「无虚拟化 = 架构层内存问题」改为「已知限制：内存随项目数线性增长，
  系数约 0.09 MB/项，实测 500 项 ≈151 MB 私有提交」。

## 四、复核中查出的真缺陷：悬浮窗 / 侧边栏没有基底 tint

### 代码链路

阶段 2 为去掉「同一像素画两遍」给 `WindowBackdropService.Attach/Apply` 加了
`paintWindowSurface`，悬浮窗/侧边栏传 `false`：

```csharp
window.Background = paintWindowSurface
    ? FindThemeBrush("BrushWindowBaseGlass") ?? Brushes.Transparent
    : Brushes.Transparent;   // ← 成功走 Acrylic 时这里是 Transparent
```

而两个窗口的根 Border 写的是：

```xml
<Border Background="{Binding Background, RelativeSource={RelativeSource AncestorType=Window}}" ... />
```

阶段 2 报告的意图是「窗口自身背景留空，**交给带圆角的子 Border 画一次**」，
但 Border 绑定的正是被置成透明的 `Window.Background` —— 结果**这层 18% 基底一层都没画上**。
四个窗口里只有悬浮窗、侧边栏是「零 tint」，其余两个是 18% 基底 + 导航/内容层。
这正是悬浮窗对比度一直垫底、且亮暗壁纸下读数一模一样的结构性原因。

### 修复（两处 XAML，各自一行）

`Views/FloatingWindow.xaml`、`Views/SidebarWindow.xaml`：

```xml
<Border Background="{StaticResource BrushWindowBaseGlass}" ... />
```

窗口表面仍留空，所以**没有**回到阶段 2 修掉的「画两遍」（有效 32.8%）。
回退到不透明底色时窗口自身是深色实心，Border 只是再压 18%，仍然可读。

### 前后对照（同一套 `phase3-readability.py`、同一组合成壁纸、真实 exe）

| 壁纸 / 窗口 | primary p50 改前 | **改后** | p95 最坏 改前 → 改后 |
|---|---:|---:|---:|
| 暗 / 全屏分类 | 6.81 | **6.81** | 3.87 → 3.87（对照组，未变） |
| 亮 / 全屏分类 | 5.17 | **5.17** | 3.81 → 3.81（对照组，未变） |
| 暗 / 悬浮窗 | 3.11 | **3.92** | 2.20 → 2.48 |
| 亮 / 悬浮窗 | 3.11 | **3.92** | 2.20 → 2.48 |
| 暗 / 侧边栏 | 8.62 | **9.18** | 3.61 → 4.46 |
| 亮 / 侧边栏 | 3.42 | **4.21** | 3.24 → 4.03 |

主窗口两行完全没动，证明改动只落在这两个窗口。
悬浮窗圆角外圈 `corner_mean 96.1 → 87.6`，仍低于内部 `98.8~100.1`，**没有出现未染色的亮环**。

### 视觉核对（真实 exe，活动窗口，DWM 读回 `BACKDROP=3`）

- 悬浮窗仍能透出背后窗口的文字，是一层半透明玻璃，**没有变成深色卡片**；
- 侧边栏贴屏幕边缘的方角干净，没有缺角；背景能透出壁纸的深红色；
- 侧边栏空状态显示的是用户拍板 A 的新文案，说明安装副本与仓库构建一致。

### 取证口径的限制（必须一起看）

这一轮悬浮窗截图的背景是一块**接近均匀的浅灰**：深色与浅色测试壁纸下读数完全相同。
从整屏原始帧看，悬浮窗背后被另一个白色应用窗口盖住，Acrylic 模糊的是那个窗口，
不是壁纸。所以这组数字应读作「**亮而均匀的背景下的最坏可读性**」，
不能当成「玻璃状态的常规对比度」。要量玻璃状态，得先清场（最小化其它窗口）
再拍；本次没有把这组数标成「通过 4.5」。

## 五、回归（串行，跑前清残留实例）

| 项 | 结果 |
|---|---|
| Release 构建 | **0 警告 0 错误** |
| 冒烟 | **460 / 460** |
| 启动（真实 exe） | **7 / 7**，冷 1.14 s / 热中位 1.14 s，`errors.log` 零增长 |
| 端到端（真实 exe + 合成鼠标） | **29 / 36 通过，7 项未验证（不是失败于改动）** |

端到端那 7 项全部是**多显示器几何**断言（Round D/E/F 及持久化）：
`EnumDisplayMonitors` 当前只返回 **1 台**显示器 `(0,0)-(2560,1440)`，
原先在左侧的 1080×1920 @150% 竖屏**不在了**，虚拟屏也从 `(-1080,-90)` 变成 `0,0 2560x1440`。
脚本里那些 `x2 < 0` / `950 <= w2 <= 1085` 的判据在单屏拓扑下不可能成立。

按「不得为了通过测试而删除断言或降低验收标准」：**不改脚本、不改判据、不把这 7 项标成通过**。
它们记为「本轮无硬件条件，未验证」；上次 36/36 是在双屏拓扑下取得的。
其余 29 项（含拖拽、八向缩放、配置损坏自愈、屏幕外位置恢复、几何持久化）全部通过。

## 七、仍未解决 / 未验证

1. **亮壁纸 p95 ≈3.7 的物理上限**：要过 4.5 需要 α≈62%，等于实心板，规格不允许。
   悬浮窗本次从 3.11 提到 3.92，仍未到 4.5，且这次量的是最坏均匀亮底。
2. **玻璃状态的常规对比度**没有可靠数字（取证时背后有白色窗口），需清场后重拍。
3. **显示器热插拔 / 锁屏恢复 / 跨天 24h+ 驻留**：本轮仍无法实测（竖屏甚至已不在拓扑里），
   沿用 `MEMORY.md` 里的 6 小时驻留无泄漏结论，不标为通过。
4. **布局切换 ~320 ms**（220 项目）是真实体感可感的量级，与投影无关；
   降它要么缓存两套视图（涨内存），要么虚拟化（动拖拽），本轮都没做。

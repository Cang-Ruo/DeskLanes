# 阶段 4：200+ 项目渲染性能（含 TextShadowGlass 开关对照）

> 一句话结论：**文字投影没有可测量的性能代价**；关掉投影反而略慢（噪声）。
> 200+ 项目下真正值得注意的是"全部瓦片实体化"带来的内存与首屏成本。

---

## 一、测试数据与方法

| 项 | 值 |
|---|---|
| 数据 | 220 个项目：12 个文件 + 3 个文件夹 + 205 个批量项；2 个分类、2 个自由分区 |
| 视口 | 点开项目最多的分类（**206 个瓦片同时实体化**，`scrollable_height = 2059 px`） |
| 进程 | `DeskLanes.UiSnapshot.exe perf200`（同一个二进制跑两组，避免编译差异） |
| 对照方式 | 环境变量 `DESKLANES_NO_TEXT_SHADOW=1` 在运行时摘掉文字投影（实测摘掉 **210** 个 `TextBlock.Effect`） |
| 采样 | 每组 **3 次**，取中位数 |
| 计时 | 首屏=进程启动到布局完成；切换=执行命令到 `ContextIdle`；滚动=**等到下一帧真的画出来**；缩放=改尺寸到布局稳定 |

### 一个测错的坑（记录备查）

滚动最初量出来 **0.3 ms**，看着像"完全不卡"。原因是只调了 `UpdateLayout()`，
而 WPF 会把布局推迟到渲染阶段——量到的是空转。改成等 `CompositionTarget.Rendering`
的下一帧才停表，数字才有意义（改后仍是 0.2 ms，但这次是真的）。

## 二、结果（3 次中位数）

| 指标 | 投影开 | 投影关 | 差异 |
|---|---|---|---|
| 首屏（进程启动→布局完成） | 5645.8 ms | 5473.3 ms | 关快 3.1% |
| 布局切换（分类 ↔ 分区） | **323.8 ms** | 345.5 ms | 关**慢** 6.7% |
| 滚动（每步到下一帧） | 0.2 ms | 0.2 ms | 无差异 |
| 缩放（改窗口尺寸） | 231.7 ms | 265.9 ms | 关**慢** 14.8% |
| 工作集内存 | 507.9 MB | 499.3 MB | 关低 1.7% |
| 托管堆 | 30.0 MB | 30.0 MB | 无差异 |
| 实体化瓦片 | 206 | 206 | — |

**判读：**

1. **投影的开销小于测量噪声**。方向还反了（关掉更慢），说明 5~15% 的差异来自
   进程启动状态/GC 时机，而不是投影本身。结论：**不需要为投影做优化**，也不必因为它
   牺牲可读性（阶段 3 正是靠它 + 局部底救回可读性的）。
2. **布局切换 324 ms、缩放 232 ms** 是真实体感可感的量级（一次切换约 1/3 秒）。
   这是 206 个瓦片重新测量/排布的成本，与投影无关。
3. **滚动 0.2 ms/步**：因为 `WrapPanel` 不虚拟化，206 个瓦片在首屏就已全部实体化，
   滚动只改偏移量、不触发重排。**流畅，但代价是内存**。
4. **首屏 5.6 s / 507 MB 要打个折扣看**：`perf200` 为了造 220 个项目，
   会先写 205 个临时文件再提取图标，这段在真实使用中不存在
   （真实是扫描桌面 + 提取图标）。所以这组数字**只能用来做两组之间的相对比较**，
   不能当成"真实首屏 5.6 秒"。

---

## 三、附带发现（不在本阶段修复范围）

- **不虚拟化 = 内存随项目数线性涨**。206 个瓦片 → 约 508 MB 工作集。
  桌面 500 个项目时会明显更重。这属于架构层问题（`WrapPanel` 换成
  `VirtualizingWrapPanel` 才能解决），不在本次视觉验收范围内，记录备查。
- 首屏里有相当一部分是**图标提取**，不是渲染。真要做首屏优化，方向是图标缓存，
  而不是动 XAML。

## 五、复核更正（阶段 7，2026-11-08）

> **本节的 507.9 MB / 499.3 MB 不能当成「真实内存占用」。**
> 它只记了 `WorkingSet64` 单次读数——这个数字由 Windows 按整机内存压力决定，
> 换一次内存环境就从 507.9 MB 变成 200 MB，且 `SetProcessWorkingSetSize(-1,-1)`
> 能立刻把它压到 30 MB。托管堆两轮都是 30 MB，说明对象数量根本没变。

复跑三次（同一二进制，指标加上私有提交与裁剪后工作集）：

| 次 | WS | 裁剪后 WS | 私有提交 | 托管堆 |
|---:|---:|---:|---:|---:|
| 1 | 200.8 MB | 30.3 MB | 276.0 MB | 29.6 MB |
| 2 | 201.2 MB | 30.8 MB | 279.0 MB | 29.5 MB |
| 3 | 196.9 MB | 30.7 MB | 277.4 MB | 29.7 MB |

稳态口径（`mem` 模式逐层拆除）：206 瓦片 → 私有提交 **128.6 MB**、托管堆 12.6 MB；
501 瓦片 → 私有提交 **150.9 MB**、托管堆 22.5 MB，约 **0.09 MB/项**。
连续切换 12 次的曲线在第 5 次后走平，强制 GC + 裁剪后回到 138.5 MB 私有提交，
**不是泄漏**。

因此第三节「附带发现」里「不虚拟化 = 500MB 量级架构层问题」更正为：
**内存随项目数线性增长，但系数很轻；本轮判定不值得为它改 `WrapPanel`**
（会牵动拖拽 / 指派 / 自由分区几何，收益远小于风险）。
同理，「关掉投影省 1.7%」也只是 WS 没被裁剪造成的读数差，不能当投影开销的证据；
「投影无可测开销」的结论本身仍成立。

完整数据与判定见 `phase7-report.md` 与 `phase7-memory.json`。

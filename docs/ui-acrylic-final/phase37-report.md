# 阶段 37：收起小球改为「细环玻璃球」三态

**范围澄清**：用户说的「悬浮窗样式太朴素」指的是**悬浮窗收起后的 3cm 小球**，
不是悬浮窗本体。本体、侧边栏、全屏窄条**这一轮完全没改**，后续再看。

先给了三份内联视觉稿（细环玻璃球 / 扫描弧 / 节点点阵），
用户选了 **A 细环玻璃球 + 静止 / 悬停 / 拖动三态都要**。

视觉证据：`phase37-ball-{idle,hover,dragging}.png`（真实 exe 的 GDI 截图）。
功能探针：`tools/phase37-ball-style-probe.py`（8 项全过）。

## 一、实现

`EdgeStripWindow` 的 `Ball` 改为一组叠放元素（都在 3cm 窗口内，留 4px 内边距，
外光环才不会被窗口边界裁掉）：

| 状态 | 细环 | 外光环 | 中心符号 |
|---|---|---|---|
| 静止 Idle | 1px 冷蓝 `#7FD8FF` | 无 | 10px 小菱形 |
| 悬停 Hover | 2px 提亮 `#B4E4FF` | 一圈更淡的冷蓝环 | 18px 放大菱形 |
| 拖动 Dragging | 1px 冷蓝**虚线** | 无 | 8px 小方块 |

- 主体玻璃始终取 `Application.Current.Resources["BrushShellGlass"]`，
  **和悬浮窗 / 全屏 / 侧栏本体是同一支画刷**；冷蓝只做点缀，不破坏阶段 33/36
  刚统一的材质。
- `CollapseVisualPolicy.ForBall(hovered, dragging)`：拖动优先于悬停，
  拖动中即使触发 `MouseLeave` 也不会被打断；松开后按鼠标是否还在球上恢复
  悬停 / 静止态。
- 所有既有交互不变：3cm、可拖动并记住位置、位移 <4px 仍算点击、
  点击展开、换分辨率时 clamp 回工作区。

## 二、验证

`phase37-ball-style-probe.py` 用真实 exe 抓三态 GDI 截图并逐像素比对：

```
静止 vs 悬停       像素差 7.98
悬停 vs 拖动中     像素差 66.01
拖动不误展开 / 位置仍落盘 / 点击仍能展开   全部通过
                                        合计 8/8
```

三张截图肉眼确认：静止是深蓝灰半透明圆 + 冷蓝细环 + 小菱形（红壁纸透出）；
悬停环明显变粗变亮且多一圈淡光环、菱形放大；拖动时环变虚线、中心收成方块。

## 三、测试链污染配置的复盘（已恢复，非产品缺陷）

全套回归里阶段 36 探针一度失败。诊断发现：多个探针串行运行时互相覆盖了
真实 `settings.json`，把 `WindowMode` 改成了 1（全屏）、悬浮窗尺寸写回
788.8×555.2，于是「等悬浮窗」的探针等到的是全屏窗口。

处理：

- `phase36-ball-probe.py`：显式声明 `WindowMode=0`、临时关闭
  「失焦自动隐藏」（该行为由 `phase35-deactivate-probe.py` 专门覆盖），
  并把一次性尺寸迁移断言改成幂等的「缩小后尺寸已生效且标记已落盘」
  （迁移算法本身由冒烟第 43 节 `FloatingSizePolicy.Compact` 覆盖）。
- `phase37-ball-style-probe.py`：同样显式声明模式；修掉一次编辑误删的换行。
- 回归结束后**主动把用户配置恢复**为应有状态并逐项核对：
  `WindowMode=0`、`FloatingWindowWidth/Height=504.56/369.24`、
  `FloatingCompactSizeMigrated=True`、
  `FloatingHideOnDeactivate/SidebarAutoCollapse` 保持用户原勾选值，
  清掉测试产生的小球位置。

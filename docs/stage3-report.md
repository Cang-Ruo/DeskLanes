## 3. 关键设计决策

1. **监听只做"登记"，扫描统一走重扫**：事件到达只记录"哪个目录变了"（防抖合并），真正同步一律通过重新扫描该目录完成。数据正确性由"扫描结果"保证，而不是由单个事件的语义保证——这是对 FileSystemWatcher 不可靠性的根本防御。
2. **范围感知的失效判定**：`ScanResult.ScopeDirectories` 只记录成功枚举的目录；合并时只有落在这些目录里的项目才可能被判定失效。目录临时不可访问、局部重扫未覆盖的目录，其项目保持原状，**不会被误伤**（有测试实证）。
3. **自定义项按磁盘存在性校正**：桌面外的自定义项目不会因为"不在桌面上"被判定失效；文件被删则失效，重新出现则自动恢复（不再依赖"每次扫描未见即失效"）。
4. **重命名迁移只在可靠时进行**：仅使用 `Renamed` 事件给出的 `OldFullPath → FullPath`（操作系统明确告知是同一个项目）。源项目不在库中、或目标路径已被另一项目占用时**不做任何猜测合并**（有测试实证）。
5. **防抖 = 滑动窗口 + 最长延迟上限**：连续事件不断重置 400 ms 窗口；为避免事件风暴下永不触发，累计等待超过 3 s 后立即执行。
6. **"已有同步在进行"时排队而不是丢弃**：一轮同步（扫描 + 保存）耗时几百毫秒，期间的新事件若被直接丢弃会真的遗漏（真实桌面实测复现过），因此放回队列并在当前轮结束后重跑，上限 12 轮，超限才放弃并交由周期性重扫兜底。
7. **周期性全量校正兜底**：默认 5 分钟一次。覆盖 FSW 的所有已知盲区（事件遗漏、缓冲区溢出、休眠唤醒、监听重建期间的变化），并顺带尝试重建失败的监听。
8. **缓冲区扩容**：`InternalBufferSize` 64 KB，降低高频事件溢出概率；即使溢出也有 `Error` 处理 + 重扫。

## 5. 本阶段发现并修复的真实缺陷

**缺陷**：真实桌面首次验收时"删除后项目被标记为失效"失败。日志显示删除事件的防抖窗口撞上一轮仍在进行的同步（一轮同步要写 36 KB×2 配置文件，耗时数百毫秒），代码当时的处理是"本次交由下一轮重扫校正"并**直接丢弃**——而该测试关闭了周期性重扫，于是变更被彻底遗漏。

**修复**：改为放回队列、等当前轮结束后自动重跑（上限 12 轮，超限才放弃交周期性重扫兜底）。

**验证**：
- 修复后真实桌面 22/22 通过，日志可见"排队等待下一轮（第 1 轮）→ 失效 1"
- 新增回归测试（`DelayedScanner` 把"扫描完成 → 合并"之间的窗口人为拉长到 700 ms）：**还原缺陷行为时测试失败（159 项 + 2 项失败）**，修复后通过（161/161）——证明这条测试真的能拦住这个 bug，而不是恒过的摆设

## 6. FileSystemWatcher 的已知局限与重扫校正机制（按要求说明）

| 局限 | 程序如何应对 |
|---|---|
| **事件可能遗漏**（缓冲区溢出、系统繁忙、网络驱动器） | `InternalBufferSize` 扩到 64 KB；`Error` 事件触发该目录立即重扫并延迟重建监听；每 5 分钟全量校正兜底 |
| **重命名不一定以 `Renamed` 送达**（可能拆成 Deleted+Created 一对） | 实测中观察到一次重命名未走迁移（表现为旧项失效 + 新条目）。此时无法可靠判定是"同一个项目"，按既有模型处理：旧路径项标失效保留配置、新路径作为新项目进入库，**绝不猜测合并**。用户手动把它拖回原分类/分区即可恢复关联 |
| **事件乱序 / 重复** | 事件只影响"哪个目录需要重扫"（去重的目录集合），顺序与次数不影响结果；数据由重扫结果决定 |
| **短时间内大量事件** | 防抖合并（400 ms 窗口 / 3 s 上限）；一轮同步进行中的事件排队不丢弃（上限 12 轮） |
| **目录暂时不可访问**（网络盘、权限抖动） | 枚举失败的目录不纳入"扫描范围"，其中项目**保持原状不误判失效**；合并整轮失败（有警告且零项目）时直接跳过合并；恢复后监听自动重建 |
| **监听启动失败** | 降级为周期性重扫，状态栏橙色提示 + `sync.log` 记录原因，功能不中断 |
| **应用休眠 / 挂起 / 长时间未刷新** | 恢复后由下一次定时校正补齐 |
| **只监听一级目录**（`IncludeSubdirectories=false`） | 与数据模型一致：项目库只收录桌面顶层条目 |
| **desktop.ini 噪音事件** | 监听层直接忽略，扫描层过滤 |
| **快捷方式目标失效**（目标在别处被删） | 属于外部目录变化，无法监听全部目标；由重扫统一刷新 `ShortcutTargetExists`（最长 5 分钟内反映） |

一句话概括：**监听负责"快"，重扫负责"对"**。所有数据最终以扫描结果为准，监听只是提前触发重扫的信号。

## 7. 诚实声明（未执行 / 未验证的部分）

1. **缓冲区溢出未真实触发**：`Error` 处理路径由"目录被删除"场景覆盖（同一代码路径），没有构造 8K+ 事件的风暴来真正打爆缓冲区。
2. **网络 / OneDrive 重定向桌面未实测**：开发机桌面是本地磁盘。降级轮询与"不可访问不误判"有测试覆盖，但真实网络盘上的表现未验证。
3. **系统休眠 / 唤醒未实测**：靠定时校正兜底，未做真实休眠往返。
4. **多实例同时运行未测**：两个实例会同时监听并写同一份配置，存在相互覆盖的可能（阶段 1 起就未做单实例互斥）。这是已知边界，建议后续阶段处理。
5. **长时间运行（数小时 / 数天）未测**：内存与日志的长期表现未验证（日志有 512 KB 截断保护）。
6. **鼠标拖拽 / 右键菜单端到端仍未测**（继承阶段 2 的声明，本阶段未触碰该部分）。
7. **真实应用里未验证"重命名以 Deleted+Created 送达"的场景**：只在实际使用中观察到过一次迹象，未复现；对应的处理逻辑（旧失效 + 新条目、不猜测合并）由单元级测试覆盖。

## 8. 已知问题与后续建议

1. **每次同步都会落盘**：即使无变化也写一次配置（36 KB×2）。目前频率低（事件驱动 + 5 分钟兜底）可接受；高频变化场景可优化为"无变化不写盘"。
2. **多实例互斥缺失**：建议下一阶段加命名互斥锁，第二个实例提示后退出。
3. **重命名迁移依赖 `Renamed` 事件**：若被拆成 Deleted+Created 则关联丢失。可选增强：合并阶段用"内容签名 + 时间戳"做启发式配对——但按"不为实时性引入难维护机制"的原则，暂不实现。
4. **UI 自动化测试缺失**（FlaUI）：拖拽、真实弹窗等交互仍未自动化。

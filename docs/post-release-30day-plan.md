# DeskLanes v0.10 发布后 30 天行动计划

> 制定于 2026-11-21。基线：v0.10 已正式公开发布。
> 原则：**不加功能、不重做 UI**。用真实用户反馈决定下一次迭代，用验证代替开发冲动。
> 当前最大风险不是功能少，而是在没有真实反馈时持续用开发替代产品验证。

---

## 总目标

让陌生用户下载、使用、反馈，形成可闭环的反馈机制；同时把可靠性与兼容性验证做扎实，
为 v0.2.x 的打磨提供依据。30 天内**不发布新版本功能**，除非出现必须修的高优先级 Bug。

## 阶段划分

| 阶段 | 天数 | 目标 |
|---|---|---|
| A · 观察与修复 | 第 1–7 天 | 确保首批用户顺利使用，建立反馈入口 |
| B · 可靠性与兼容性 | 第 8–21 天 | 多显示器/DPI/资源占用/大规模项目验证 |
| C · 首次体验与流程固化 | 第 22–30 天 | 规划 onboarding，固化发布流程，汇总决策 |

---

## 阶段 A：观察与修复（第 1–7 天）

**目标**：首批用户能顺利下载、安装、运行；反馈有地方提、有人看。

### 第 1 天 — 发布面检查
- [ ] 打开 Release 页，确认两个 ZIP + SHA256SUMS 均可下载
- [ ] 用浏览器（无登录）复现一次下载 → 解压 → 运行，确认 SmartScreen 说明准确
- [ ] 确认 README 首屏截图与 v0.10 一致、链接无 404
- [ ] 记录 Release 下载数与当前 Issue 数为基线

### 第 2 天 — 反馈入口上线
- [x] 建立 `.github/ISSUE_TEMPLATE/`：Bug Report / Feature Request / 使用问题
- [x] 配置 `config.yml`（关闭空白 Issue，引导到文档与 Release）
- [ ] 确认三个模板在 GitHub 页面正常显示
- [ ] 在 README 增加「反馈与 support」小节，链接到 Issues

### 第 3 天 — 诊断包闭环
- [ ] 自己走一遍「设置 → 导出诊断包」，确认 zip 内容不含私人敏感信息
- [ ] 在 Bug 模板里已提示诊断包；确认用户知道**什么时候该用**（窗口错位、扫描异常、启动失败）
- [ ] 写一段 3 行说明放进 README：出问题先导出诊断包再提 Issue

### 第 4–5 天 — 每日巡检
- [ ] 每天固定时间看一次 Issues / Release 评论
- [ ] 按标签分类：安装问题 / 运行异常 / 使用疑问 / 功能建议
- [ ] 高优先级 Bug（崩溃、数据丢失、无法启动）当天响应，其余 48 小时内响应
- [ ] 记录出现频率最高的 3 个问题

### 第 6 天 — 首轮问题处理
- [ ] 能复现的高优先级 Bug 立即修；不能复现的请用户补诊断包
- [ ] 使用疑问直接回复并把答案沉淀进 README/FAQ
- [ ] SmartScreen 反馈：若多人遇到，在 Release 顶部加醒目说明

### 第 7 天 — 阶段 A 复盘
- [ ] 统计：下载数、Issue 数、关闭数、分类分布
- [ ] 写一页简短复盘：用户最容易卡在哪一步
- [ ] 决定：是否需要一个 hotfix（仅当存在阻断性 Bug）

**阶段 A 交付物**：反馈入口可用、首批问题清单、一页复盘。**不新增功能。**

## 阶段 B：可靠性与兼容性（第 8–21 天）

**目标**：桌面管理软件的核心竞争力是稳定——多显示器、混合 DPI、位置恢复决定长期留存。

### 第 8–9 天 — 多显示器测试矩阵（上）
按场景逐项验证，记录结果到 `docs/multi-monitor-matrix.md`：

| 场景 | 必测 |
|---|---|
| 双屏 100% / 100% | 窗口与小球跨屏移动 |
| 双屏 100% / 125% | 混合 DPI 切换 |
| 双屏 100% / 150% | 高 DPI 可读性 |
| 主屏在左、副屏在右 | 坐标变化 |
| 主屏在右、副屏在左 | 负坐标 |

> 注：本机当前为双屏，可完成大部分；无法覆盖的组合用代码审查 + 文档标注。

### 第 10–11 天 — 多显示器测试矩阵（下）
| 场景 | 必测 |
|---|---|
| 副屏在主屏上方 | 负 Y 坐标 |
| 拔掉副屏 | 窗口回归可见范围 |
| 插回副屏 | 位置恢复与重排 |
| 睡眠唤醒 | 所有模式位置 |
| 远程桌面连接与断开 | DPI 与窗口位置 |

### 第 12–13 天 — 资源占用分析（只测量，不优化）
分阶段采样 WorkingSet，找出占用来源：

| 场景 | 测量目标 |
|---|---|
| 仅托盘驻留 | 最低驻留内存 |
| 悬浮球驻留 | 增量 |
| 悬浮窗展开 | 增量 |
| 全屏展开 | 增量 |
| 侧栏展开 | 增量 |

重点调查：WPF 控件保留、图标缓存（上限 512）、BitmapSource 占用、
BlurEffect/DropShadowEffect、不可见窗口的视觉树、模式切换是否重复建资源。

**先确定来源，再决定是否优化。不要把 340 MB 当成必须降到 50 MB 的硬指标。**

### 第 14–15 天 — 大规模项目测试
- [ ] 用 `--demo` 注入 200 / 1000 个项目，测启动时间、扫描耗时、UI 响应
- [ ] 观察图标缓存与布局开销的拐点
- [ ] 记录到 `docs/scale-test.md`

### 第 16–17 天 — 配置健壮性
- [ ] 配置损坏恢复已在冒烟覆盖；再人工验证：版本过新、字段缺失、文件被占用
- [ ] 确认备份机制不会无限累积
- [ ] 验证诊断包在异常配置下仍可导出

### 第 18–19 天 — 反馈闭环检查
- [ ] 每个已关闭 Issue 是否有明确结论（已修/设计如此/无法复现）
- [ ] 高频问题是否沉淀进 README 或文档
- [ ] 考虑是否开启 Discussions（**仅当你愿意长期维护**；否则不开）

### 第 20 天 — Bug 修复窗口
- [ ] 集中处理阶段 B 发现的高优先级问题
- [ ] 只修 Bug，不加功能

### 第 21 天 — 阶段 B 复盘
- [ ] 汇总兼容性结论：哪些环境稳定、哪些有问题
- [ ] 更新 `known-limitations.md`（如发现新的限制）
- [ ] 输出下一版可靠性清单

**阶段 B 交付物**：多显示器矩阵、资源分析、大规模测试、可靠性清单。**仍不发布新功能。**

## 阶段 C：首次体验与流程固化（第 22–30 天）

**目标**：为 v0.2.x 的 onboarding 做准备，同时把发布流程固定下来。

### 第 22–23 天 — 首次使用体验评估
- [ ] 找 1–2 个陌生用户（或自己模拟全新状态）计时：第一分钟能否理解软件
- [ ] 列出卡点：怎么呼出、怎么建分类、怎么拖动、三种模式区别
- [ ] 只读观察，不马上做引导系统

### 第 24–25 天 — Onboarding 方案（设计，不实现）
按 3 步轻量引导设计，写成方案文档：

| 步骤 | 内容 | 目的 |
|---|---|---|
| 01 | 欢迎来到 DeskLanes | 一句话：整理桌面，但不移动文件 |
| 02 | 认识三种工作空间 | 图示介绍悬浮/全屏/侧栏 |
| 03 | 快捷键与悬浮球 | 马上知道怎么打开和收起 |

最后一屏文案：**你的桌面，从现在开始更有序。按 Ctrl+Alt+Space 打开 DeskLanes。
桌面项目将自动同步。分类只是虚拟整理，不会移动原始文件。**

设计原则：可跳过、只在首次启动出现、不做复杂教程系统。

### 第 26–27 天 — 发布流程固化
把 v0.10 的实际发布步骤写成 `docs/release-pipeline.md`：

1. 修改功能与修复
2. Debug / Release 构建
3. 自动化测试（冒烟 + 真实交互）
4. 真实环境验收
5. 检查版本号与 Release Notes
6. 生成 self-contained 包
7. 生成 portable 包
8. 计算 SHA256
9. 检查 ZIP 文件结构
10. 生成 Release Notes
11. Git Tag
12. 发布 GitHub Release

> 暂不把所有测试搬到 CI。先让本地脚本可靠，再把重复劳动自动化。

### 第 28 天 — 版本号规则
- [ ] v0.10 已发布，**保留不改名**（历史发布不重写）
- [ ] 确定后续规则并在 README/CHANGELOG 写明：小修 / 功能 / 大功能 / 成熟 分别如何命名
- [ ] 注意：v0.10 与历史 v0.2.0 的先后关系容易让用户困惑，下一版应明确延续或跳跃规则

### 第 29 天 — 30 天总复盘
- [ ] 汇总：下载、Issue、修复、兼容性发现、用户卡点
- [ ] 回答一个问题：**真实用户最需要什么？**
- [ ] 据此决定 v0.2.x 的 1–2 个重点，而不是列一堆想做的功能

### 第 30 天 — 决策日
- [ ] 若反馈平静、无阻断问题：进入阶段 C 的 onboarding 实现（下一个周期）
- [ ] 若有明确高频需求：按优先级排入 v0.2.x
- [ ] 若发现严重兼容性问题：优先修复，发布 hotfix

**阶段 C 交付物**：onboarding 设计方案、发布流程文档、版本规则、下一步决策。

## 明确不做的事（30 天内）

| 项 | 建议 | 原因 |
|---|---|---|
| 自动更新 | 暂缓 | 覆盖安装已够，先有用户 |
| 插件系统 | 暂缓 | 复杂度高，无需求证据 |
| 云同步 | 暂缓 | 违背本地优先的简单性 |
| AI 功能 | 暂缓 | 易偏离桌面整理核心 |
| 大规模 UI 重设计 | 暂缓 | 冰晶轻玻璃体系已形成 |
| ARM64 | 暂缓 | 先验证 x64 用户需求 |
| 国际化 | 暂缓 | 先让当前产品稳定 |
| 更多窗口形态 | 暂缓 | 三种已足够 |

## 每日节奏（建议）

- **上午 15 分钟**：看 Issues / Release 反馈，分类标记
- **白天**：当天主题任务（按上面日程）
- **晚上 10 分钟**：记录当天发现到 `docs/feedback-log.md`（没有就写"无新增"）

## 成功标准（30 天后）

1. 用户有明确的地方反馈，且每个反馈有响应
2. 多显示器/混合 DPI 有实测结论，不再靠假设
3. 资源占用有来源分析，不是盲目优化
4. 首次体验有评估与设计方案
5. 发布流程固定成文档，下次发布不再靠记忆
6. **没有因为"想加功能"而偏离真实反馈**

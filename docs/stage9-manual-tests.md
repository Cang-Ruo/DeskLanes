# 阶段 9 · 手动补测清单（公开发布标准）

> 建立时间：2026-10-29
> 依据：`docs/competitive-landscape.md`（竞品调研）、`docs/stage8-plan.md` §6.4（8.4 遗留）
> 定位：项目已确定**公开发布、争取用户**，因此补测标准按"发给陌生人用、不能出事"来定，
> 而不是"自己能用就行"。
> 原则：**每个测试项必须有可判定的客观判据**，不写"感觉流畅"这类主观标准。

## 通用规则

1. 改缩放后**必须注销重登**（或重启），否则 DPI 不真正生效——这是 8.4 第一轮踩过的坑。
2. 每个场景都要**同时截图**：一张整屏（含任务栏，用来证明分辨率/缩放在屏内）、一张窗口局部。
3. 失败判据一律写进"已知限制"文档，**不得宣称已通过**。
4. 测试用的是 `publish/vm-package/DeskLanes.exe` 的自包含版
   （65,068,384 B，MD5 `13d5e69d848a51a57fb96a0039ce4e4f`）。
   项目已于 2026-10-29 由 DeskSpace 更名为 DeskLanes，下文所有路径均按新名。

## 测试环境（2026-10-29 确认）

| 屏幕 | 物理分辨率 | 缩放 | 逻辑分辨率（应用实际看到的） | 说明 |
|---|---|---|---|---|
| 本机主屏 | 2560 × 1440（横） | 125% | 2048 × 1152 | **125% 档本机已有历史证据** |
| 本机副屏 | 1080 × 1920（**竖屏**） | 150% | **720 × 1280** | 混合 DPI + 竖屏，见 A3 |
| 虚拟机 | 1920 × 1080（横） | 100% | 1920 × 1080 | 干净环境，专测 100% / 低分辨率 |

这套配置**天然就是混合 DPI 双屏**（125% + 150%），A3 可直接在本机做，不必等虚拟机。
其中**竖屏副屏是最有价值的场景**：逻辑分辨率 720×1280 极窄极高，此前从未测过。

### 已知高风险点（先记下，测出来再定处置）

- **悬浮窗默认 780×540 逻辑像素，竖屏副屏逻辑宽度只有 720** → 溢出 60 像素。
  且 `FloatingWindowWidth/Height` 至今仍是**死字段**（用户无法手动缩小窗口）。
  只要悬浮窗落到竖屏副屏、或该屏被设为主屏，几乎必然超出边界。
- 全屏工作空间在 720 逻辑宽度下，分类面板 + 项目网格可能被挤到截断。
- 侧边栏展开态 280×760 尺寸上能塞进 720×1280，但**贴边停靠是否跟对屏幕**未验证。

### A2 - 复核 175% 那条存疑记录（2 分钟）

上一轮 150% 那批的环境取证截图上，Windows「设置 › 系统 › 屏幕」的「缩放」读数是 **175%**，
与标注的 150% 不一致。

> **2026-10-29 结论：识图读数不可信，不要再用截图当环境证据。**
> 本轮用系统 API 直接取值，主屏 125%、副屏 150% 与用户报告完全一致；
> 但同一批里主屏那张设置页被识图读成 150%（真实 125%）。
> 环境取证今后一律用 `EnumDisplayMonitors` + `GetDpiForMonitor`，
> 历史 175% 那条记录按「无法复现」结案。

步骤（改为）：不再依赖截图，直接在目标机跑一次取值脚本，把输出贴进证据目录。
判据：脚本输出的 DPI 与用户声明的缩放一致。

### A3 - 副屏停靠 / 混合 DPI / 竖屏（**已有证据：竖屏这一档未达标**）

> **2026-10-29 实测**：竖屏副屏（逻辑 720×1280）上，全屏工作空间右侧被截断、
> 悬浮窗宽度溢出。三项独立证据互相印证，详见
> `docs/stage9-4-floating-drag-resize-and-fullmode.md` §七。
> **修法不在本阶段**（需响应式布局 + 标题栏窄态折叠，触碰 UI 冻结约束），
> 已登记为阶段 10 任务。此处保留步骤，供修完后复测。

> **本机即可做**：现有配置已是混合 DPI 双屏（主 2560×1440@125% + 副 1080×1920@150% 竖屏），
> 不必等虚拟机，也不必再接第三块屏。

步骤：
1. 设置 → 系统 → 显示 → 点「标识」，确认哪块是 1 哪块是 2，记下各自缩放值
   （当前应为 主 125% / 副 150%，即混合 DPI）
2. 切**侧边栏**模式 → 看它贴在哪块屏的边缘 → 拖到另一块屏 → 看停靠边跟不跟着走
   → 主屏、副屏各停靠一次（左/右都试）
3. 切**悬浮窗**模式 → 拖到竖屏副屏 → **重点看是否超出屏幕宽度**（见下方高风险点）
4. 切**全屏**工作空间 → 在竖屏副屏上看分类面板与项目网格有没有被挤到截断
5. 锁屏 → 唤醒
6. 拔掉副屏 → 等 10 秒 → 再插回
7. 改一次主屏分辨率，再改回来

判据（客观）：
- 侧边栏**始终贴在它所在那块屏**的边缘，不会跑到另一块屏，也不会半个身子出屏
- **悬浮窗在任何屏上都完整在屏内**（竖屏副屏逻辑宽度仅 720，是重点）
- 全屏工作空间在 720 逻辑宽度下无文字截断、无控件重叠
- 拔插与改分辨率后，窗口仍完整可见（不为 NaN、不为屏外坐标）
- 混合 DPI 下文字不模糊、不被拉伸缩放

实测结果（2026-10-29）：

| 判据 | 结果 | 证据 |
|---|---|---|
| 悬浮窗在任何屏上都完整在屏内 | ❌ 780 DIP > 720 DIP，溢出 60 DIP（物理 90 px） | 脚本实测：拖到副屏后物理宽 1170 vs 显示器 1080；副4/副6 边缘被截 |
| 全屏工作空间在 720 宽下无截断 | ❌ 右侧按钮文字与项目图标被切（`MinWidth=900` 本身就超） | 副1（自由分区）、副2（分类视图） |
| 侧边栏不出屏 | ✅ 未见出屏（但遮挡了桌面图标） | 副5 |
| 混合 DPI 下文字不模糊 | ✅ 未见模糊或拉伸缩放 | 主屏 125% 全部 7 张、副屏 150% 全部 7 张 |
| 拔插 / 改分辨率后窗口仍完整 | ⬜ 本次未测 | — |

> 竞品参照：DeskBox 把"格子绑定到显示器硬件标识、每种连接组合独立布局"当作主打能力。
> 本项目这一项连数据都没有，是发布前最大的空白。
> 竖屏是额外加分项——竞品里明确提竖屏的也很少，如果这一档能过，可以写进发布说明。

## B 类：竞品已覆盖、本项目无数据

### B5 - 长时驻留资源占用

竞品参照：DeskBox 公开称"全部格子打开时内存稳定在约 50 MB"，并做了 AOT 内存曲线测量。

步骤：开机自启后**静置 8 小时不操作**（中间锁屏一次），分别在 T0 / T+4h / T+8h 记录：
任务管理器里的**内存（专用工作集）**、**句柄数**、**线程数**、**GDI 对象数**。

判据：内存不持续增长（8 小时内增幅 < 20%，且无明显单调上升曲线）；句柄/线程/GDI 不单调增长。

### B6 - 大量项目时的性能

步骤：往桌面堆到 **200+ 个项目**（可用脚本批量造快捷方式，测完删掉），记录三项耗时：
① 冷启动到主窗口可见 ② 首次扫描完成 ③ 从分类视图切到自由分区视图。

判据：冷启动 < 3 秒；扫描 < 5 秒；切换无明显卡顿（< 1 秒）。
同时看 `logs/errors.log` 是否新增内容（应为 0 增长）。

### B7 - Windows 10 兼容性

背景：Mica 需要 Build ≥ 22621，Win10 会走**不透明回退**分支——代码写了但**从未实测**。

步骤：在 Win10（建议 19041 或 22H2）上装自包含版，跑一遍三种模式。

判据：
- 窗口**能正常显示**（不能白屏、黑屏、不显示，也不能只有边框没有内容）
- 悬浮窗/侧边栏（分层窗口）玻璃底色正常，不是全黑或全透明
- 托盘、快捷键、开机自启三项都能用

### B8 - 锁屏唤醒 / 远程桌面 / 睡眠恢复

这三个场景最容易让分层窗口（悬浮窗/侧边栏）跑到屏外或变透明。

每个场景后检查：窗口是否仍完整在屏内、能否正常呼出、`settings.json` 里的窗口坐标是否为有限值。
判据：三个场景下窗口均可见且可交互，配置里不出现 NaN / Infinity。

## C 类：核心卖点验证（"三形态共用一套数据"）

> C9 / C10 我会写成可执行脚本，见 `tests/` 下新增的验收程序，不需要手工点。
> 下面只列**必须人工肉眼确认**的补充项。

### C9 - 三模式来回切换的数据一致性（人工部分）

脚本会断言 JSON 层面的数据一致；人工需确认**视觉层面**也一致：

步骤：全屏模式建 3 个分类、拖 5 个项目进去、在自由分区里手动摆好位置并记录坐标 →
切悬浮窗 → 切侧边栏 → 再切回全屏。

判据：分类列表、项目归属、分区坐标、窗口位置偏好**全部保持**；三个模式下同一个项目的
图标与名称一致。

### C10 - 配置损坏后的真实恢复（人工部分）

脚本会断言"不崩 + 有备份"；人工需确认**提示是否友好**：

步骤：手动把 `settings.json` 改成非法 JSON → 启动应用。

判据：
- 应用不崩溃、不卡死
- 有用户能看懂的提示（不是英文异常堆栈）
- `%LocalAppData%\DeskLanes\backups\` 里留下了损坏前的原件
- 再用「导出诊断包」导一次，包里的 `manifest.txt` 能列出这份备份
